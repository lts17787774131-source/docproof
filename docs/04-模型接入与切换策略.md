# 模型接入与切换策略：Ollama 先行 → DeepSeek 收尾

> 硬件：RTX 4060 8G（~272 GB/s 带宽，fp16 够用，支持 FlashAttention）
> 约束：先用本地 8B 跑通，DeepSeek 的 key 留给终版
> 结论：**方案成立，但有两个必须提前接受的现实**

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 能不能先用 Ollama 8B | **能，而且应该**：MVP-1 全本地跑通，零 API 成本、零网络变量、能离线演示 |
| 8B 能出终版数字吗 | **不能**。8B Q4 在中文财报表格题上明显弱于 DeepSeek，终版必须用它复跑 |
| 那消融怎么办 | **消融固定用 8B**（看相对增益），**终版只用 DeepSeek 跑 B0 和 B6 两组**（看绝对水平 + 生成器贡献） |
| VLM 读图怎么办 | **DeepSeek 官方 API 是纯文本，不能读图**。L3 要么本地 3B VLM、要么别家 API、要么先降级为 caption 检索 |
| 显存够吗 | 8B(4.9G) + reranker int8(0.6G) ≈ **6.3G**；embedding 走 CPU。**不要试图同时把 bge-m3 放进 GPU** |
| 最大的坑 | Ollama 是独立进程，它和你 PyTorch 进程各占一份显存 + 各有一份 CUDA context |

---

## 1. 为什么"Ollama 先行"是对的

**三个理由**：

1. **迭代不花钱、敢乱试**：消融要跑 7 组 × 100 题，本地跑 0 成本，调参时不会心疼。
2. **没有网络变量**：调参最怕"这次分数变了是因为网络抖动或模型被静默升级"。
3. **离线可演示**：面试现场没网也能跑。

**两个前提（不满足就别开始）**：

1. **固定生成器**：同一组消融必须同模型、同 prompt 版本、同 temperature（评测用 0）。换一个变量，数字就不可比。
2. **明确它是"开发期模型"**：你最终要报告的是**系统能力**，不是"这个 8B 的能力"。所以报告里必须有两套数字：相对增益（本地）与绝对水平（云端）。

---

## 2. 三条 provider 组合

| 组合 | 生成 | 向量/重排 | 适用阶段 | 单题成本 | 端到端延迟 |
|---|---|---|---|---|---|
| **A 全本地** | Ollama 8B | CPU | MVP-1 前段（打通链路） | 0 | 12–18s |
| **B 混合** | Ollama 8B | GPU（批处理）/ CPU（交互） | MVP-1 后段（跑消融） | 0 | 12–18s |
| **C 全云** | DeepSeek | 本地 | MVP-2 终版评测、Demo | 极低 | 2–4s |

> 建议路线：**A → B →（MVP-2 末）C**。不要在 MVP-1 就接 API，否则你会分不清"是检索改好了还是模型变强了"。

---

## 3. 显存冲突的真相（最容易翻车的地方）

Ollama 是**独立进程**。它占的显存和你 PyTorch 进程占的显存是两笔账，而且**各自都有一份 CUDA context**（各 0.3–0.5G）。

| 同时加载 | 估算 | 结果 |
|---|---|---|
| 8B Q4 (4.9G) + bge-m3 (2.2G) + 两份 context (0.8G) | **7.9G** | 卡在边缘：一有波动就 OOM，或者悄悄掉到 CPU 变龟速 |
| 8B Q4 (4.9G) + reranker int8 (0.6G) + 两份 context (0.8G) | **6.3G** | ✅ 稳 |
| 8B Q4 + KV(4k, q8) 单独 | 5.7G | ✅ 很稳 |

### 解法：显存按任务阶段分配（两条路径）

**交互路径（用户问答）**

```
CPU:  query embedding（单条 0.2–0.4s）
  ↓
GPU:  向量检索 + reranker int8（0.6G）
  ↓
GPU:  Ollama 8B 生成（4.9G + KV）
```

**批处理路径（建索引 / 批量跑检索指标）**

```
1. Ollama keep_alive=0  →  卸载 8B，释放 5.7G
2. PyTorch 加载 bge-m3 到 GPU（2.2G）→ 批量 embed（300 块 3–8s）
3. 卸载 bge-m3  →  下次交互时 Ollama 重新加载 8B（首次 5–10s）
```

**一句话总结（面试可以直接说）**：

> "我的显存不是常量，是**按任务阶段分配**的：交互时全给生成，批处理时全给向量化。"

## 4. Ollama 参数清单（照抄即可）

| 参数 | 建议 | 为什么 |
|---|---|---|
| 模型 | `qwen3:8b` 或 `qwen2.5:7b-instruct` | 中文财报术语明显强于 llama3.1:8b；**qwen3 记得关思考模式**，否则延迟翻倍 |
| `num_ctx` | 4096（表格题 8192） | 上下文越长 KV 越吃显存 |
| `num_parallel` | 1 | 8G 上开并发只会互相拖慢 |
| `keep_alive` | 交互 10m / 批处理 0 | 批处理前必须卸载，否则 embedding 上不了 GPU |
| KV cache 类型 | `q8_0` | KV 显存直接减半 |
| FlashAttention | 开 | 省显存 + 提速 |
| `num_predict` | ≥ 512 | 防止答案被截断（很常见的坑） |
| temperature | 0（评测）/ 0.3（演示） | 评测要可复现 |

## 5. 速度与吞吐（4060 8G 的合理预估）

| 指标 | 预估 | 依据 |
|---|---|---|
| 生成速度 | 30–40 tok/s | 4.9G 权重 ÷ 272GB/s 带宽的理论值再打七折 |
| 预填充 | 400–700 tok/s | 3k 上下文约 4–7s |
| **单次问答** | **12–18s** | 3k 输入 + 300 输出 |
| **100 题一组** | **25–35 分钟** | 这是你的迭代节奏上限 |
| **300 题 × 7 组** | **8–12 小时** | 只能夜间跑 |

**由速度反推的三条纪律**：

1. **迭代用 100 题子集**（按题型分层抽样），单组 25 分钟，一天能跑 3–4 组。
2. **300 题全量只在两个节点跑**：MVP-1 结束、MVP-2 结束。
3. **终版数字用 DeepSeek 跑**：2–4s/题，300 题约 15–20 分钟。

> 这三条不是"优化建议"，是**项目能不能按期完成的决定性约束**。8B 本地跑 2100 次要一整夜，你不会有耐心调参。

## 6. 把"8B 与 DeepSeek 的差距"变成结论（而不是短板）

| 组 | 生成器 | 题量 | 用途 |
|---|---|---|---|
| B0–B6 | Ollama 8B（固定） | 100 题迭代 + 300 题终跑 | **模块贡献**（相对增益） |
| B0' / B6' | DeepSeek（固定） | 300 题 | **绝对水平 + 生成器贡献** |

能得出的结论（这才是资深的地方）：

- "检索链路把 Recall@5 从 0.58 提到 0.88，这部分增益**与生成器无关**，换任何模型都成立。"
- "换 DeepSeek 后总体再涨 __pp，但表格题的剩余错误仍集中在 E3（表头错配）和 E10（口径），说明**换模型救不了解析和检索的问题**。"

> 这句话在面试里的杀伤力，远大于"我用了最强模型"。它证明你分得清"模型能力"和"系统能力"。

---

## 7. DeepSeek 接入的三个注意

1. **它是文本模型**：`deepseek-chat` / `deepseek-reasoner` 不接受图片输入 —— **L3 不能用它**（以你开通时的官方文档为准）。
2. **长上下文是优势**：表格 HTML + 父块可以给得更完整，对 L2 有直接收益。
3. **批量评测尽量错峰**：官方通常有夜间/批量优惠，300 题全量放晚上跑。

## 8. L3（读图）的三条路，按性价比排序

| 方案 | 成本 | 质量 | 建议 |
|---|---|---|---|
| ① **不做视觉直读**：用 caption + 邻文 + 表格 HTML 回答 | 0 | 中（图表题偏弱） | **MVP-2 默认方案**，诚实写进"局限性" |
| ② **本地 Ollama 3B VLM**（qwen2.5vl:3b，~2.5G） | 0，但与 8B 时间片切换（每次 3–6s） | 中低 | MVP-2 末尾试点，**只在 T4 题上用** |
| ③ **别家 VLM API**（Qwen-VL / GLM-4V） | 低 | 高 | V1.5 想冲图表题时再上 |

**判断标准**：② 相对 ① 在 T4 上提升 **< 10pp 就果断放弃**，把时间放回表格题——表格才是你差异化的地方。

## 10. 兜底：Ollama 出问题怎么办

| 故障 | 现象 | 处理 |
|---|---|---|
| 模型被卸载 | 首次请求卡 5–10s | 预热一次；`keep_alive` 调大 |
| 掉到 CPU | tok/s 掉到 3–5 | 降 `num_ctx`；关掉其他占显存的程序 |
| 答案被截断 | 输出突然断在半句 | `num_predict` 调到 512+ |
| 术语/单位错 | "万元"读成"元" | 换 qwen 系列；prompt 里附术语表与单位说明 |
| 思考模式太慢 | 回答前一大段推理 | qwen3 关闭 thinking，或换 qwen2.5:7b-instruct |

## 11. 本周的 Ollama 接入动作（1–2 小时）

1. `ollama pull` 目标 8B → 跑一次"3k 上下文 + 300 输出"的计时，记录 **tok/s 和首字延迟**（这两个数决定你的评测节奏）。
2. 用一条真实的表格 HTML 问一个数值问题，看它会不会算错——**这是你对 8B 能力上限的第一手判断**。
3. 把这两个数字写进 `docs/bench-ollama.md`，后面所有排期都基于它。
