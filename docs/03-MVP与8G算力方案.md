# MVP 与 8G 算力落地方案

> 配套 `00-开发计划.md` 的 4.3 / 4.4 / 第九章。
> 三个约束：**8G 显存**、**MVP 先跑通**、**AI 应用 : 后端 ≈ 7:3**。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 8G 能跑这个项目吗 | **能**。起步做 Ollama 8B 全本地（峰值 ~6.3G），终版切 DeepSeek；两条路线的账本见 `04-模型接入与切换策略.md` |
| 8G 能跑 7B VLM 吗 | **别试**。能"不 OOM"，但并发 1、分辨率被压、每页 20–30s，跑 1800 次评测要十几小时，还会拖垮演示 |
| MVP 要多久 | **MVP-1（4 周，80h）** 打通文本 + 表格链路并出分；**MVP-2（2 周，40h）** 加 VLM 路由（另接视觉模型）和演示 |
| 最先该验证什么 | **显存账本**（30 分钟）+ **B0 基线**（半天）。这两件事决定后面 8 周的方向 |
| 最容易被问倒 | "没有 GPU 你怎么做评测？" → 答：本地跑检索，云端跑生成，provider 抽象 + 固定版本 + 成本计量 |

## 1. MVP 边界（先做哪一半）

### 1.1 三段交付

| 阶段 | 周期 | 包含 | 明确不包含 | 交付标志 |
|---|---|---|---|---|
| **MVP-1** | 4 周 / 80h | 解析、DocIR、结构切分、dense+BM25 检索、重排、文本/表格生成、B0 基线 | VLM 路由、引用校验、拒答、服务化 | 能对 80 题跑分，B0→B4 出数 |
| **MVP-2** | 2 周 / 40h | 引用校验、阈值拒答、VLM 路由（另接视觉模型）、Gradio 高亮、300 题全量消融 | 压测、限流、成本面板 | 能录 3 分钟 Demo，消融表完整 |
| **V1.5** | 3 周 / 60h | 队列、进度、幂等、限流退避、缓存、成本面板、压测报告 | 多租户 RBAC、K8s、灰度 | 可交付、可复现 |

### 1.2 MVP-1 的最小闭环（只做这 6 件事）

1. PDF → 文本层 + 版面块 + 表格 HTML（带 cell bbox）
2. 块 → DocIR（page / bbox / reading_order / section_path）
3. DocIR → 父子块（子块检索、父块送生成）
4. 子块 → bge-m3 向量 + BM25 → RRF 融合
5. Query → top-30 → reranker → top-5
6. top-5 → API 文本 LLM → 答案 + `[E1]` 引用编号

**不在 MVP-1 做的事**：VLM、拒答、流式、前端高亮、并发、缓存。全部后移。

> 判断标准很简单：**MVP-1 结束时要能回答"结构切分到底有没有用"，其他都是次要的。**

## 2. 8G 显存账本

> ⚠️ 本节是「**检索本地 + 生成上云**」的账本。**如果你先用 Ollama 8B 全本地（推荐起步），账本不一样**——8B 常驻 GPU、embedding 走 CPU，见 `04-模型接入与切换策略.md` 第 3 节。两套账本不要混用，否则一定 OOM。

### 2.1 常驻 vs 按需

| 组件 | 显存 | 策略 | 备注 |
|---|---|---|---|
| bge-m3（embedding） | 2.2G | **常驻** | 查询和索引都要用 |
| bge-reranker-v2-m3 | 2.2G | **按需**，空闲 5 分钟卸载 | 只在重排时用 |
| DocLayout-YOLO | 0.6G | **按需**，解析完即卸 | 也可以用 CPU |
| CUDA context + 激活 | 0.6–0.8G | — | 容易被忽略，必须算进去 |
| **峰值** | **~5.8G** | | 8G 卡留 ~2G 给 Windows 桌面 |

### 2.2 分阶段加载（关键设计）

```
任务类型            加载顺序                        峰值
─────────────────────────────────────────────────────────
解析（PDF→IR）      DocLayout(0.6) → [OCR 在 CPU]   0.6 + 0.8 = 1.4G
索引（IR→向量）     bge-m3(2.2)                     3.0G
查询（问题→答案）   bge-m3(2.2) → +reranker(2.2)    5.8G → 卸 reranker 回 3.0G
```

**规则**：

- 同一个 Worker 串行处理，**同一时刻最多 2 个模型在显存里**
- 加载失败（OOM）→ 自动降级到 CPU 版本 + 记录告警，**不中断任务**
- 启动时探测可用显存，动态决定 embedding 的 batch size（8 / 16 / 32）

> 这段"账本 + 分阶段"就是面试时"你 8G 怎么跑"的标准答案，比说"我用了量化"具体得多。

## 3. 模型 Provider 抽象（8G 方案的骨架）

**原则：业务代码永远不直接调某个厂商的 SDK。**

| 概念 | 说明 |
|---|---|
| `TextProvider` | 输入 messages + 证据块，输出 text + tokens_in/out + latency |
| `VisionProvider` | 输入 messages + 页图（base64 或 URL），同上 |
| `provider 配置` | 名称、base_url、model、timeout、max_retries、单价（成本计量用） |
| `路由` | L1/L2 走便宜文本模型，L3 走 VLM；失败自动 fallback 到备用 provider |
| `版本锁定` | 评测配置里写死 provider + model + prompt_version，**换模型必须重跑全量** |

**三条纪律**：

1. **评测与演示分离配置**：演示可以切便宜/快的，评测必须固定，否则数字不可比。
2. **每次调用都记账**：tokens_in / tokens_out / 单价 / 累计成本，写进 trace。
3. **超时 + 重试 + 熔断**：429 和超时是常态，尤其免费额度。默认 3 次指数退避，连续失败切 fallback。

## 4. 性能预算（8G + API，50 页有文本层的年报）

### 4.1 索引阶段

| 步骤 | 目标耗时 | 瓶颈 |
|---|---|---|
| 文本层抽取 | 2–5s | PyMuPDF，很快 |
| 版面检测 | 5–10s（GPU）/ 25–50s（CPU） | 按需加载 |
| 表格结构识别 | 1–3s/表 × 10–20 表 | **CPU 是主要瓶颈** |
| 切分 + DocIR | <1s | 纯 CPU |
| embedding（约 300 块） | 3–8s | batch 16 |
| 入库 | <2s | pgvector |
| **合计** | **30–60s** | 扫描件走 CPU OCR 则 3–6 分钟 |

### 4.2 查询阶段

| 步骤 | 目标耗时 | 备注 |
|---|---|---|
| query 归一化/改写 | 0.3–0.8s | 可先用规则，省一次调用 |
| 混合检索 | 50–150ms | 本地 |
| 重排（30→5） | 80–200ms | GPU |
| 生成（流式） | 1.5–4s | 首字 0.5–1s |
| 引用校验 | 0.3–0.8s | 规则优先，LLM 兜底 |
| **p95** | **3–5s** | 网络波动是主要变量 |

> 8G 的代价不是"慢"，是"**必须串行**"。所以并发能力靠队列 + 缓存补，而不是靠堆显存。

## 5. API 成本控制（4 招 + 1 条预算线）

| 招 | 做法 | 省多少（预期量级） |
|---|---|---|
| 缓存 | 同文档同问题直接返回；query embedding 缓存；解析结果缓存 | 30–50% |
| 证据压缩 | 父块截到 2k token；表格只传表头 + 相关行 | 30–40% |
| 路由 | L1 用便宜模型；只有图表/低置信才上 VLM | L3 占比压到 20% 以内 |
| 批处理 + 限流 | 评测并发 2–4，令牌桶控速 | 避免 429 重试浪费 |

**预算线**：

- 开发期全本地（Ollama）= **0 成本**；只有终版要给钱：B0/B6 各 300 题 ≈ **600 次调用 ≈ 3M token**，量级**几十元**（按实际单价换算）
- **先跑 20 题**估算单题成本，再决定要不要全量跑
- 设日预算告警：超过阈值自动停止评测任务（防止调参时跑飞）

## 6. 8G 环境上的 5 个坑

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | Windows 桌面吃显存 | 明明 8G，`torch` 只看到 7.2G | 启动时按**可用**显存算 batch，别写死 |
| 2 | Docker/WSL2 显存开销 | 容器里再跑模型，OOM | **MVP 阶段模型跑原生 Windows**，Docker 只装 Postgres/MinIO/Redis |
| 3 | CPU OCR 慢 | 扫描件 50 页 5 分钟+ | 只对无文本层的页 OCR；dpi 压到 150–200；只有表格页做结构识别 |
| 4 | reranker 反复加载 | 每次查询都加载，慢且抖 | 懒加载 + 空闲 5 分钟卸载 + 常驻 embedding |
| 5 | 显存碎片 | 跑几小时后突然 OOM | 固定 batch、避免动态 shape、定期回收 |

> 第 2 条最容易被忽略：**很多人 8G 卡上跑 Docker Desktop + WSL2，模型还没加载就先被吃掉 1G**。MVP 阶段用原生 Python 跑模型，数据服务才进容器，能省掉一半玄学问题。

## 7. MVP 验收清单（DoD）

### MVP-1（第 4 周末）

- [ ] 3 份不同版式 PDF 全部解析成功，表格可用率 ≥ 80%
- [ ] 每道题返回 page + bbox，前端（哪怕是本地 HTML）能画出框
- [ ] 80 题跑分：文本类 ≥ 60%，表格类 ≥ 45%（B0 预期 30–40%）
- [ ] `python -m docproof.eval.run --config mvp1.yaml` 一条命令出报告
- [ ] 显存峰值 < 7G，连续跑 100 次查询不 OOM
- [ ] 有一张"结构切分 vs 定长切分"的对比表（哪怕样本只有 80 题）

### MVP-2（第 6 周末）

- [ ] 300 题全量跑分，B0→B4 消融表填满
- [ ] 引用准确率 ≥ 85%，误拒率 < 10%
- [ ] T4 图表题：L3 路由比纯文本高 ≥ 20pp
- [ ] 3 分钟演示视频（含高亮）
- [ ] 每题 token 与费用可见

### V1.5（第 9 周末）

- [ ] 50 页 PDF 3 分钟内 ready，进度可见
- [ ] 10 并发 p95 < 5s，429 自动恢复
- [ ] 成本面板：按文档/按天统计
- [ ] README 陌生人能跑通

## 8. 什么时候该升级硬件

| 信号 | 动作 |
|---|---|
| 300 题 × 7 组跑不完一夜 | 按小时租 24G，跑完即退（一次几十元） |
| 需要"本地 7B vs API"对比数据 | 租 24G，做一个附录实验 |
| 演示要求离线/断网 | 本地 3B 版，接受质量下降 |
| 有真实用户/要长期跑 | 再考虑买卡或云主机 |

> 结论：**8G 足够撑到"有完整数据 + 能演示"，升级的时机由实验需求触发，而不是由焦虑触发。**

## 9. 本周（W0）三件事（8G 版）

1. **本地模型 smoke test（1 小时）**：`ollama pull` 8B，跑一次「3k 上下文 + 300 输出」的计时，记录 **tok/s 与首字延迟**；再单独加载 bge-m3 看显存占用。**这两个数决定你的评测节奏，先测再谈架构。**
2. **选 8 份 PDF + 出 30 题**（不是 15 份 300 题，先小后大）：覆盖文本/表格/图各 10 题。
3. **跑 B0（半天）**：用你现有的文本 RAG 跑这 30 题，记下分数与错题类型。

> 30 题跑完，你会知道两件事：**表格题到底有多差**、**你的解析链路能不能撑住**。这两件事比任何架构图都重要。
