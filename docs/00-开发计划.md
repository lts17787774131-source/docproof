# DocProof（卷证）开发计划

> 面向中文财报 / 政务文档的**可溯源多模态文档问答**系统
> 版本 v1.0 ｜ 状态：待评审 ｜ 适用：AI 应用岗（主）/ 后端岗（次）

> **实现进度（2026-11-16）**：MVP-1 已跑通，真实数字见 [v0.1 评测报告](eval-report-v0.1.md)。
> 本文档中的 52%→79%、0.58→0.88 等均为**目标值**；合成集实测 **46.9%→98.4%**（模板题 + 题型算子的上限），
> 真实年报口语提问 **13/15 = 87%**（加"主体/报表名"标签与表单解析后）。

## 0. 一页速览

| 项 | 结论 |
|---|---|
| 项目名 | **DocProof（卷证）**——"每一句回答都有出处" |
| 一句话 | 把 PDF 里的表格、图、跨栏正文变成带「页码 + 坐标」的**证据单元**，让回答能点回原文，证据不足时敢拒答 |
| 定位 | 不是"又一个 RAG"，而是**用实验证明纯文本 RAG 在哪失效、怎么修** |
| 主贡献 | ① DocIR 文档中间表示 ② 结构感知父子块 + 三路检索路由 ③ 引用校验与阈值拒答 |
| 量化目标 | 答案准确率 52%→79%，表格子集 31%→74%，Recall@5 0.58→0.88，引用准确率→93%，p95 12s→3.5s |
| 周期 | **MVP-1 约 80h（4 周）→ MVP-2 约 40h（2 周）→ V1.5 约 60h（3 周）** |
| 算力 | **4060 8G**：开发期 Ollama 8B 全本地（峰值 ~6.3G），终版切 DeepSeek（见 4.3 / 04 文档） |
| 最大风险 | **版面/表格解析质量**——瓶颈在数据入口，不在模型 |
| 最容易被问倒 | "79% 怎么测的？谁标的？提升来自哪一步？" → 第 8 章就是为了回答这个 |

> ⚠️ 全文百分比均为**目标值**，必须用实测数字替换。方案给的是"怎么测出可信数字"的方法，不是虚构的战绩。

## 1. 先说清楚：面试官判断"深度"的 6 条判据

你担心项目"太基础"，本质不是技术栈不够新，而是**没有可验证的论证结构**。资深面试官看项目，只在这 6 个地方找证据：

| # | 判据 | 面试官心里的问题 | 普通项目的表现 | 本项目怎么满足 |
|---|---|---|---|---|
| 1 | **有基线** | "这个 90% 是和谁比？" | 只报绝对值 | B0 = 你已有的文本 RAG，冻结后逐步加模块 |
| 2 | **有归因** | "提升来自哪一步？" | "我加了重排就好了" | 6 组消融，每次只改一个变量 |
| 3 | **有取舍** | "为什么不用 X？" | 什么新用什么 | 5 条 ADR，写清「选了什么、代价是什么」 |
| 4 | **有工程约束** | "500 页要跑多久？10 个并发呢？" | 没想过 | 显存预算表 + 延迟分解 + 压测报告 |
| 5 | **有失败分析** | "它错在哪？" | 只展示成功案例 | 10 类错误码 + 每轮迭代的占比变化 |
| 6 | **有边界** | "什么做不了？" | 万能 | 明确的「不做清单」+ 拒答机制 |

**结论：深度 = 可证伪的论证，不是技术名词的数量。** 这套项目把 6 条全部占满。

## 2. 对你原方案的诊断（9 条，逐条修）

原方案方向是对的（多模态文档 RAG 确实是当前招聘热点），但它是"课程作业级"的模块清单，不是"可交付、可论证"的系统。核心问题如下：

| # | 原方案 | 问题 | 后果 | 本方案的修正 |
|---|---|---|---|---|
| 1 | 通篇按「模块」组织，无基线 | 没有 baseline，任何提升都无法证明 | 面试只能说"我用了 XX 技术" | **W0 先建 B0 基线并冻结**，后续每步只加一个变量 |
| 2 | "100 条测试集就够了" | 100 题上 5pp 的差异大概率是噪声 | 数字经不起追问，一问就崩 | 300 题分层 + 置信区间 + McNemar 配对检验 |
| 3 | 表格"结构识别转 markdown" | Markdown **丢失单元格坐标与合并信息** | 无法高亮定位、无法核对数字；长表直接超上下文 | 表格存 **HTML + cell bbox**，Markdown 仅作为喂 LLM 的序列化视图 |
| 4 | "BGE / CLIP 系列"混着用 | CLIP 对密集小字检索很弱；两套向量空间混检需要额外对齐设计 | 召回不稳，且说不清为什么 | 主路 bge-m3（dense+sparse）+ BM25；视觉检索只作为**图表页的可选一路**，单独消融 |
| 5 | VLM 直读 vs OCR 文本，二选一 | 真实问题是**成本-精度的权衡**，应按题型路由 | 要么贵得离谱，要么图表题全错 | 三档路由 + 准确率/成本**帕累托曲线**实验 |
| 6 | FastAPI + Gradio 就是"服务化" | 只是 demo 形态，没有工程纵深 | 后端岗一个都答不上 | 异步任务、对象存储、幂等、限流、可观测、压测 |
| 7 | 没有引用校验、没有拒答 | 企业文档场景，**答错比不答贵** | 不可用，也不敢演示 | 强制引用 + entailment 校验 + 阈值拒答 |
| 8 | 没有 token / 延迟预算 | 50 页 PDF 全量喂 VLM 不现实，演示会卡死 | 现场翻车 | Token 预算表 + 分层策略 + 缓存（见 4.3、6.2） |
| 9 | "创新点列 4 个，挑 2 个做" | 学生思维：贡献不聚焦 | 讲不清"你做了什么" | **1 主 + 2 辅**，主贡献必须一句话说清且可测量 |

另外两个隐性风险：

- **和已有项目同质**。你做过智能问答，如果新项目还是"文档问答"，HR 会觉得重复。破解方法不是换赛道，而是**把旧项目变成基线**："我先做了文本版，发现表格题只有 31%，才有了这一版。"
- **被质疑"调包"**。现在 MinerU / RAGFlow / Dify 都能做出 80% 的效果。所以必须有一个**开源方案里没有、且能消融证明有效**的东西——DocIR + 结构切分 + 路由就是。

## 3. 项目定位：初心、用户、边界

### 3.1 初心（面试第一句话的模板）

不要说"因为多模态 RAG 很火"。用四段式，每段一句话：

```
【场景】我在 ______（实习/课程/帮导师/帮家里）时，需要在 ______ 页的 ______ 里找 ______。
【痛点】我翻了 ______ 分钟，最后发现关键信息在 ______（第几张表 / 哪张图）。
【失效点】我之前的文本 RAG 在这类问题上只有 ______ 分，因为它把表格拍平成一行字，
         数字和表头对不上，图里的信息它根本看不见。
【取舍】所以我把目标从"答得像不像"改成"能不能指到原文那一格"，
       宁可拒答，也不给一个无法核对的数字。
```

> 例（**请替换成你的真实经历**，HR 会追问细节）：
> "帮做投研的朋友查一份 180 页的年报，找'Q3 单季毛利率'，翻了半小时。我发现他不是不会问，是系统答不了——关键数据在合并报表的跨页表格里，纯文本 RAG 把表头和三行数据切散了，模型编了个看起来很像的数。从那天起我给这个项目定的第一指标就不是'答对率'，而是'每个数字能不能点回原文那一格'。"

**这条故事线同时回答了三个问题**：初心是什么、项目能干嘛、你和别人做的有什么不一样。

### 3.2 用户与场景

| 用户 | 真实任务 | 一句话价值 | 愿意付费的理由 |
|---|---|---|---|
| 投研 / 行研 | 年报、招股书里跨页找数、做同比 | 30 秒定位到那张表那一行 | 时间 = 钱 |
| 审计 / 合规 | 合同条款、附注、关联交易 | 每个结论可追溯、可留痕 | 出错要担责 |
| 政企知识库 | 红头文件、招投标、政策汇编 | 引用原文，避免"编政策" | 合规红线 |

### 3.3 一句话价值 & 不做什么

**价值**：把"整份文档"变成"可检索、可核对、可拒答的证据库"。

**不做（写进 README，面试主动说）**：

- 不做通用聊天助手（那是 ChatGPT 的活）
- 不自研 OCR / 版面模型（用成熟件，把精力放在"表示与检索"上）
- 首版不做 PPT / Excel / 手写体
- 不做多轮 Agent 自动规划（除非 V2，且必须有评测支撑）

> 主动说"不做什么"，是资深度的最强信号。

### 3.4 与已有项目的关系（重要）

| | 旧项目（智能问答） | 新项目（DocProof） |
|---|---|---|
| 输入 | 纯文本 / 网页 | PDF（版面、表格、图） |
| 单元 | 定长 chunk | DocIR 结构块 + 父子块 |
| 检索 | 单路向量 | 混合 + 路由 + 重排 |
| 输出 | 一段话 | 答案 + 引用 + 置信度 + 可拒答 |
| 角色 | **基线 B0** | 迭代后的系统 |

**叙事**："旧项目不是黑历史，是我这次实验的对照组。" —— 这一句能直接把"项目重复"的质疑变成"有迭代方法论"的加分项。

### 3.5 成功指标

| 类型 | 指标 | 目标 |
|---|---|---|
| 北极星 | **证据可采纳率**：答案正确 且 引用块确实包含证据 且 人能 3 秒核对 | ≥ 75% |
| 体验护栏 | 误拒率（能答的题被拒） | ≤ 8% |
| 性能护栏 | p95 端到端延迟（文本路径 / VLM 路径分开报） | 3.5s / 7s |
| 成本护栏 | 单份 50 页文档索引成本 + 每 100 次问答成本 | 见 6.4 |

## 4. 可行性分析

### 4.1 技术可行性（按模块看成熟度）

| 模块 | 成熟度 | 主要不确定性 | 应对 |
|---|---|---|---|
| PDF 文本层提取 | 高 | 扫描件无文本层 | 有文本层走 PyMuPDF，无则走 OCR |
| 版面检测 | 中高 | 多栏、跨页表、印章 | DocLayout-YOLO + 人工抽检 20 页校准 |
| 表格结构识别 | **中（最大瓶颈）** | 合并单元格、无线表、跨页续表 | PP-StructureV3 + 复杂表回退「表格截图给 VLM」 |
| DocIR 设计 | 高（自研可控） | 过度设计 | 只保留"检索/引用/展示"三者需要的字段 |
| 切分策略 | 高 | 规则太碎或太粗 | 父子块 + 参数扫描（256/512/1024） |
| 向量 + BM25 | 高 | 中文分词、表格数字 | jieba 自定义词典 + 数字归一化 |
| 重排 | 高 | 512 token 截断长表 | 分段打分取 max，或只对表头+关键行打分 |
| VLM 生成 | 中高 | 图表读数、幻觉 | 路由 + 引用校验 + 拒答 |
| 服务化 | 高 | 长任务、并发 | 队列 + 进度 + 幂等（见 M7） |
| 评测 | 中 | 标注成本、主观性 | 强模型初标 + 人工复核 30% |

**结论：除表格解析外，全部是成熟工程问题。** 而表格解析恰好可以用"降级策略"兜住——这就是可行性高的根本原因。

### 4.2 数据可行性

| 来源 | 用途 | 注意 |
|---|---|---|
| 巨潮资讯 / 上市公司年报（公开） | 中文主力，表格密集 | 只用于本地研究，不二次分发 |
| 政府公开文件 / 招投标公告 | 版式多样、扫描件 | 可覆盖 OCR 场景 |
| DocVQA / ChartQA | 英文对照、证明方法可迁移 | 不追求刷榜，只做 sanity check |
| TAT-QA / FinQA | 表格数值推理题型参考 | 借题型，不借数据 |
| 自建 300 题 | **主评测集** | 见 8.1，这是核心资产 |

**标注成本估算**：300 题 × 平均 6 分钟（出题 + 标证据块 + 写标准答案）≈ 30 小时。用强模型初标可压到 12-15 小时 + 人工复核。

### 4.3 算力可行性（8G 显存的现实约束）

**先说结论：8G 跑不动"可用的 7B VLM"，但完全不耽误 MVP。**

Qwen2.5-VL-7B 即使 AWQ 4bit，权重也要 5.5–6.5G，加上视觉编码器、激活值和 KV Cache，在 8G 上只能"勉强不 OOM"：并发 1、输入分辨率被压到 640 左右、每页 20–30s。这个状态**做不了评测**——300 题 × 7 组消融 ≈ 2100 次推理，要跑十几个小时，还没法演示。**硬上 7B 是这个项目最大的时间陷阱。**

**推荐架构：Ollama 8B 先行，DeepSeek 收尾**（细节见 `04-模型接入与切换策略.md`）

| 组件 | 放在哪 | 显存 | 说明 |
|---|---|---|---|
| Ollama 8B（生成） | GPU 常驻（交互）/ 卸载（批处理） | ~4.9G + KV | MVP-1 主力；终版换 DeepSeek API |
| bge-m3（embedding） | **CPU**（交互）/ GPU（批处理） | 0 / 2.2G | 单条 query 0.2–0.4s，可接受 |
| bge-reranker（ONNX int8） | GPU | ~0.6G | 与 8B 共存 |
| DocLayout-YOLO | GPU 按需 / CPU | ~0.6G | 50 页只需 5–10s，用完即卸 |
| PaddleOCR PP-StructureV3 | **CPU** | 0 | 财报大多有文本层，OCR 只处理扫描件 |
| 生成（VLM 读图） | 本地 3B / 别家 API | — | **DeepSeek API 无视觉**，L3 需另接（见 04 §8） |
| **GPU 峰值** | | **~6.3G** | 留 ~1.5G 给 Windows 桌面 |

**三条硬规则**：

1. **不在本地跑 7B VLM**。真想本地视觉，只考虑 3B 级别（qwen2.5vl:3b ≈ 2.5G），且仅用于补 T4；**消融用本地 8B、终版用 DeepSeek，两套数字分开报告**。
2. **显存按任务阶段分配**：交互时全给生成（8B 常驻）、批处理时卸载 8B 再上 embedding、解析阶段只加载 layout。**同一时刻最多两个模型在显存里**。
3. **所有模型调用走 Provider 接口**，本地/云端一行配置切换；**评测时锁定 provider + 模型版本**，否则分数会漂。

**为什么 OCR 放 CPU 还能接受**：中文年报 80% 以上有文本层，PyMuPDF 直接抽，根本不用 OCR；只有扫描件（政务/招投标）才走 PP-Structure，50 页约 3–5 分钟——而这是异步任务，用户看不到等待。**这条是 8G 方案能成立的关键。**

**升级路径**：

| 阶段 | 算力 | 触发条件 |
|---|---|---|
| MVP-1 | 8G（Ollama 8B 全本地） | 现在 |
| MVP-2 | 8G（Ollama 为主 + 少量 DeepSeek 对比） | 需要终版数字时 |
| V1.5 | 8G + DeepSeek API | 只加服务化与前端，不需要更多显存 |
| V2 | 按小时租 24G | 要跑全量消融对比（含本地 7B）时，租一晚 |
| V3 | 自有 24G / 双卡 | 要接真实用户 |

> 一句话：**8G 决定的是"生成先本地、后上云"，不是"项目做不了"。** 而接入 API 之后，"限流 / 退避 / 缓存 / 成本归因"从纸面需求变成真问题——正好补上你 3 成后端的分数。

### 4.4 时间可行性（MVP 优先）

| 阶段 | 内容 | 工时 | @20h/周 |
|---|---|---|---|
| **MVP-1** | 评测基座 + 解析 + DocIR + 切分 + 检索 + 文本/表格生成 | 约 80h | 4 周 |
| **MVP-2** | 引用校验 + 拒答 + VLM 路由（另接视觉模型）+ 高亮 + 全量消融 | 约 40h | 2 周 |
| **V1.5** | 服务化精简 + 压测加固 + 前端 + 打磨 | 约 60h | 3 周 |
| 合计 | | 约 180h | 9 周 |

**建议**：**先只承诺 MVP-1 的 4 周**。4 周后你会拿到 B0→B4 的分数——用真实数字决定要不要继续投入，而不是先押上 9 周。这也是对 HR 最诚实的说法："我先用 4 周验证方案可行性，跑出数据再决定投入多少。"

### 4.5 岗位匹配度（一套项目，两种讲法）

| 考察点 | AI 应用岗 | 后端岗 | 本项目覆盖 |
|---|---|---|---|
| 模型选型与评测 | 必考 | 少 | 消融矩阵 + 帕累托曲线 |
| RAG 链路设计 | 必考 | 少 | 全链路自研，不用框架黑盒 |
| 数据建模 | 中 | 必考 | DocIR / 索引 schema / 元数据过滤 |
| 服务设计 | 少 | 必考 | 队列 / 幂等 / 对象存储 / 状态机 |
| 并发与性能 | 少 | 必考 | 压测报告 / 缓存 / 限流 / 降级 |
| 可观测性 | 少 | 必考 | trace / 指标 / 成本面板 |
| 交付规范 | 中 | 必考 | ADR / README / 评测报告 / 一键起服务 |

**讲法差异**：

- 面 AI 岗：重点讲 **8 章评测** + **6.2 的 5 个取舍**，工程部分一句带过。
- 面后端岗：重点讲 **M7 服务化** + **10 章的并发/幂等/降级**，模型部分一句带过。
- 面"AI+后端"混合岗：讲 **"为什么这个系统的瓶颈在工程而不在模型"** —— 这是最能体现复合能力的角度。

**按你的权重（AI 应用 : 后端 ≈ 7:3，可回调到 6:4）**：

| 部分 | 投入占比 | 内容 |
|---|---|---|
| 评测 + 检索 + 生成（AI 主线） | ~70% | 消融、路由、引用、拒答 |
| 服务化（后端） | ~20% | 只做"能讲清"的四件事：异步队列、幂等、限流重试、成本/trace |
| 文档与叙事 | ~10% | README、评测报告、Demo、复盘 |

> 后端这 3 成的正确用法不是"少做"，而是"**做窄**"：M7 只保留队列 + 进度 + 幂等 + 限流 + 成本面板，**砍掉多租户 RBAC、K8s、灰度发布**。面试时能讲清"为什么必须异步""幂等键为什么用文件哈希""429 和超时怎么兜"就足够，不需要真上一套 K8s 演示。如果面到 6:4 的岗位，再补"缓存三层 + 压测报告"这两块即可。

### 4.6 可行性结论

**可行，但必须砍范围。** 砍掉：

- ❌ 自研版面/OCR 模型
- ❌ 本地跑 7B VLM（8G 跑不动，生成走 API）
- ❌ 视觉向量检索作为主线（只作可选消融）
- ❌ 多轮 Agent 规划
- ❌ PPT/Excel/多语言
- ❌ 前端做完整产品（只做"高亮 + 引用"这一件事，做精）

保留 3 件事做深：**表示（DocIR）、检索（结构切分+路由）、可信（引用+拒答）**。

## 5. 核心功能模块拆解

### 5.1 架构总览

```
┌─────────────────── 接入层 ───────────────────┐
   Web（PDF 高亮）/ REST / SSE 流式
┌─────────────────── 服务层 ───────────────────┐
   写入：上传 → 预签名 URL → 对象存储 → 任务入队 → Worker → 状态推送

┌─────────────────── 能力层 ───────────────────┐
   DocIR │ 结构切分 │ 向量+BM25 │ 重排 │ VLM/LLM │ 引用校验
┌─────────────────── 数据层 ───────────────────┐
   MinIO │ Postgres + pgvector │ Redis │ 评测集
┌─────────────────── 观测层 ───────────────────┐
   trace_id 贯穿 │ 阶段耗时 │ token 成本 │ 评测报告
```

### 5.2 模块清单（M0–M8）

| 模块 | 优先级 | 工时 | 依赖 | 一句话验收 |
|---|---|---|---|---|
| M0 评测基座 | P0 | 14h | — | 300 题 + B0 基线分数 + 一键跑分脚本 |
| M1 解析层 | P0 | 26h | — | 20 页抽检，正文/表格/图 召回 > 90% |
| M2 DocIR | P0 | 12h | M1 | 每个块有 page/bbox/reading_order，可视化可查 |
| M3 切分 | P0 | 16h | M2 | 证据块被切断率 < 8% |
| M4 索引 | P0 | 10h | M3 | 单文档索引 < 60s，支持元数据过滤 |
| M5 检索 | P0 | 22h | M4 | Recall@5 ≥ 0.85 |
| M6 生成 | P0 | 26h | M5 | 带引用输出，引用准确率 ≥ 90% |
| M7 服务化 | P1 | 22h | M6 | 精简版：队列 + 进度 + 幂等 + 限流 + 成本面板（不做多租户/K8s） |

#### M0 评测基座（先做这个，反直觉但最重要）

**为什么先做**：没有尺子就盖楼，最后一定返工。90% 的课程项目死在这里。

- **输入**：15-20 份公开 PDF
- **输出**：`eval/datasets/gold.jsonl`（300 题）+ `eval/reports/b0.json`
- **关键设计**：
  - 题型分层（6 类，见 8.2），每类 ≥ 30 题
  - 每题标注**金标证据块**（page + block_id + 答案最小充分集）
  - 评分脚本一条命令跑完，输出总准确率 + 分题型 + 引用准确率 + 拒答率
- **验收**：`python -m docproof.eval.run --config b0.yaml` 能复现出同一个分数（±0.5pp）
- **面试亮点**："我第一周没写业务代码，先花 14 小时把尺子造出来。"

---

#### M1 解析层

- **输入**：PDF
- **输出**：`page.png`（200 dpi）+ 原始 layout JSON
- **关键设计**：
  - 分层：有文本层 → PyMuPDF 抽字符与坐标；无文本层 → 整页 OCR
  - DocLayout-YOLO 出 block 类别（标题/正文/表格/图/公式/页眉页脚）
  - 表格：PP-StructureV3 → HTML + 单元格 bbox；**识别置信度低或结构异常 → 存表格截图，标记 `table_image_only`**（这是保底路线）
  - 图表：裁图 + 关联 caption（"图 2"就近匹配）+ 前后各 1 段说明文字
  - 页眉页脚、水印、页码：识别后剔除，但保留在元数据里
- **验收**：抽检 20 页（含 5 页复杂表），正文/表格/图 三类 block 召回 > 90%，表格结构人工判定"可用于回答"的比例 > 75%
- **面试亮点**：解析失败不是异常，是**设计内的一等公民**（降级路径是一等公民）。

---

#### M2 DocIR（主贡献 ①）

统一中间表示，所有下游模块只认它。**字段只保留三类用途：检索、引用、展示。**

| 字段 | 用途 | 说明 |
|---|---|---|
| `doc_id` / `page_no` / `block_id` | 引用 | 全局唯一，可回指 |
| `type` | 检索 | text / title / table / figure / formula / caption / footer |
| `bbox` | 引用+展示 | 归一化坐标（0-1），换分辨率不用重算 |
| `reading_order` | 切分 | 多栏排序依据 |
| `section_path` | 检索+展示 | 如「第三节 管理层讨论 > 3.2 主营业务分析」 |
| `text` | 检索 | 纯文本视图 |
| `html` | 生成 | 表格结构视图（Markdown 只是它的降级序列化） |
| `cells[]` | 引用 | r/c/rowspan/colspan/bbox/text |
| `caption` | 检索 | 图/表标题，单独向量化 |
| `parent_id` | 切分 | 父子块关系 |

- **验收**：`/debug/doc/{id}/page/{n}` 能返回叠加了 bbox 的页面图，肉眼可核对
- **面试亮点**：被问"你的数据模型怎么设计的"，这一张表就是答案；能讲清"为什么 bbox 用归一化坐标"这种细节。

---

#### M3 结构感知切分（主贡献 ②的一半）

| 规则 | 原因 |
|---|---|
| 标题**不单独成块**，并入下属段落，并写入 `section_path` | 标题单独检索会污染结果 |
| 表格**整表一块**，超长按行切但**每片重复表头** | 表头丢失是表格问答第一大死因 |
| 图 = 图 + caption + 前后各 1 段 | 图的语义在周围文字里 |
| 跨页续表检测并合并（表头相似 + 列数一致 + 相邻页） | 财报高频场景 |
| 数字与单位、百分号、括号负号**不可切断** | 切断即歧义 |
| 父子块：子块 256-512 token 用于检索，父块 1200-2000 token 送生成 | 检索要准，生成要全 |

- **验收**：人工检查 50 个"金标证据块"，被切断或表头丢失的比例 < 8%
- **面试亮点**：能画出"为什么定长切分会切坏表格"的对比图（一张图讲 3 分钟）。

---

#### M4 索引

- **三套索引**：dense（bge-m3）+ sparse（BM25，jieba 自定义词典）+ 元数据（doc/章节/类型/页码）
- **多向量策略**：表格块同时索引 ①HTML 摘要 ②表头 + 关键行 ③caption；图索引 caption + 邻文
- **验收**：50 页文档端到端索引 < 90s（有文本层）；支持 `type=table` 这类过滤
- **面试亮点**：讲清"为什么表格要建多个向量，而不是一个"。

---

#### M5 检索（主贡献 ②的另一半）

```
Query → 归一化/改写 → 意图路由（5 类）→ 各路召回 → RRF 融合 → 重排 → 证据组装
```

| 意图 | 例子 | 策略 |
|---|---|---|
| 数值型 | "Q3 营收同比多少" | 表格优先，top-k=10，带表头 |
| 定位型 | "图 2 的实验设置" | 图 caption 优先 |
| 定义型 | "什么是关联交易" | 正文优先 |
| 跨页/多跳 | "对比 2022 和 2023 的毛利率" | 多查询展开 + 分组检索 |
| 不可回答 | "2025 年的营收" | 触发拒答判定 |

- **融合**：RRF（无需调权重，比加权求和稳）
- **重排**：bge-reranker-v2-m3，长表分段打分取 max
- **验收**：Recall@5 ≥ 0.85，Recall@10 ≥ 0.92；路由准确率 ≥ 85%
- **面试亮点**：路由不是为了炫技，是为了**省钱**（只有 20% 的查询需要 VLM）。

---

#### M6 生成（主贡献 ③）

**三档策略 + 路由**（这是"成本-精度帕累托"的来源）：

| 档位 | 做法 | 适用 | 相对成本 |
|---|---|---|---|
| L1 | 证据文本 → 文本 LLM | 定义型、正文型 | 1x |
| L2 | 证据文本 + 表格 HTML → 文本 LLM | 表格数值型 | 1.2x |
| L3 | 页面截图 → VLM 直读 | 图表、复杂版式、L2 置信度低 | 8-15x |

> **本项目的 L3 走独立视觉模型**（本地 3B 或别家 API），不塞进 8B 里；**DeepSeek 官方 API 无视觉能力**。路由的价值因此从"省显存"变成"**省钱 + 省延迟**"，这让帕累托曲线成为真正的产品决策依据。

**引用与拒答**：

1. Prompt 强制输出 `[E1]` 这样的证据编号，禁止无引用断言
2. 后校验：引用块是否**蕴含**该句（小模型或规则 + LLM judge 兜底）
3. 置信度 = 检索分 + 引用校验分；低于阈值 → 拒答
4. **拒答也给价值**：返回"最接近的 3 个候选区域"，让用户自己判断

- **验收**：引用准确率 ≥ 90%，误拒率 ≤ 8%，不可回答题拒答率 ≥ 85%
- **面试亮点**："我们的目标不是答对率最高，而是**错的时候你知道它错了**。"

---

#### M7 服务化（后端岗的主战场）

| 能力 | 设计要点 | 面试可讲 |
|---|---|---|
| 上传 | 预签名 URL 直传 MinIO，API 不转发大文件 | 为什么不走后端中转 |
| 异步 | Redis 队列 + Worker；任务状态机 `queued→parsing→indexing→ready→failed` | 长任务为什么不能用同步请求 |
| 进度 | SSE 推送分阶段进度（解析 60% / 索引 30%） | 用户体验与连接管理 |
| 幂等 | 文件 sha256 去重，重复上传直接返回已有 doc_id | 幂等键怎么选 |
| 租户/权限（可选） | `tenant_id` 行级过滤 | 7:3 阶段不做；面 6:4 或企业岗再补，**能讲清思路即可** |
| 缓存 | 解析结果、query embedding、答案（同一文档同一问题） | 三层缓存各自的失效策略 |
| 限流 | 按租户 token bucket；VLM 路径单独限流 | 保护 GPU |
| 重试 | 指数退避 + 死信队列 + 失败原因回传 | 可观测的失败 |
| 降级开关 | GPU 队列积压 → 自动切 L1/L2 路径 | 有损服务好过不可用 |

- **验收**：50 页 PDF 3 分钟内 ready；10 并发查询 p95 < 5s；压测报告进 README

## 6. 技术栈

### 6.1 选型总表

| 层 | 选型 | 为什么 | 备选 / 风险 |
|---|---|---|---|
| 语言/运行时 | Python 3.11 + uv | 生态全、依赖快 | — |
| API | FastAPI + Pydantic v2 | 异步原生、SSE 方便、类型即文档 | Litestar |
| 文本层 | PyMuPDF | 快、坐标准 | pdfplumber（慢但表格线好） |
| 版面 | DocLayout-YOLO | 轻量、中文文档表现稳 | PP-DocLayout |
| OCR/表格 | PaddleOCR PP-StructureV3 | 表格结构 + 单元格框 | MinerU（一体化，但黑盒） |
| 向量 | bge-m3（dense+sparse） | 中英混合、长文本、一模型两用 | bge-large-zh、云端 embedding |
| 稀疏 | BM25 + jieba | 数字、专有名词强 | — |
| 重排 | bge-reranker（ONNX int8 优先） | 中文强；0.6G 可与 8B 共存 | bge-reranker-v2-m3（fp16 2.2G，装不下时让位） |
| 生成（开发期） | **Ollama 8B**（qwen3:8b / qwen2.5:7b-instruct） | 零成本、离线、无网络变量 | 12–18s/题，跑不动全量 → 用 100 题迭代集 |
| 生成（终版） | **DeepSeek API** | 便宜、中文强、2–4s/题 | 无视觉能力 → L3 另接 |
| VLM（可选） | 本地 qwen2.5vl:3b / 别家 API | 补图表题 | 与 8B 时间片切换，只在 T4 用 |
| 向量库 | Postgres 16 + pgvector(HNSW) | 一份库搞定元数据 + 向量 + 过滤 | Qdrant / Milvus |
| 对象存储 | MinIO | 本地 S3 兼容，可无缝上云 | 直接 S3 |
| 队列 | Redis + Arq | async 一致、代码量小 | Celery（重） |
| 前端 | 先 Gradio，后 React + pdf.js | 高亮要靠 pdf.js 的坐标能力 | 纯 HTML 也行 |
| 观测 | structlog + Prometheus + Grafana | 成本低、可截图进 PPT | Langfuse（LLM trace） |
| 部署 | Docker Compose | 一条命令起全栈 | K8s（面试可讲不落地） |

### 6.2 五个关键取舍（ADR，面试必讲）

| # | 决策 | 选项 | 选择 | 理由 | 代价 |
|---|---|---|---|---|---|
| D1 | 表格表示 | Markdown vs HTML+bbox | **HTML+bbox** | 要引用就必须有坐标；合并单元格只有 HTML 能表达 | 存储变大、prompt 变长 |
| D2 | 切分 | 定长 vs 结构 | **结构优先，定长兜底** | 表格/图一旦切断就永久丢信息 | 规则多、边界情况多 |
| D3 | 检索 | 单路 dense vs 混合 | **dense+sparse+RRF** | 财报数字、专有名词靠向量召回不稳 | 复杂度上升，需要融合 |
| D4 | 生成 | 全 VLM vs 文本优先 | **文本优先 + 路由到 VLM** | 全 VLM 成本高 8-15 倍，且延迟不可接受 | 需要判断何时升级 |
| D5 | 框架 | LangChain vs 薄封装 | **薄封装** | 黑盒链路无法消融、无法定位失败点 | 前期要多写代码 |

> D5 是面试加分项："我不用 LangChain 不是因为它不好，是因为**我需要能单独关掉每一层做消融**。"

### 6.3 明确不用什么

- ❌ LangChain / LlamaIndex 全家桶（可用其工具函数，不用其 Chain）
- ❌ 视觉向量检索作主线（ColPali 类只作 V2 对照实验）
- ❌ 微调（除非最后一周有余力，且必须有评测证明）
- ❌ 多智能体框架（本项目不需要）

### 6.4 资源与成本清单

| 项 | 单机 MVP | 说明 |
|---|---|---|
| GPU | 1 × 8G（4060） | 开发期跑 8B + reranker（~6.3G）；embedding 走 CPU |
| CPU/RAM | 8C / 32G | 解析与 CPU OCR 吃的是 CPU |
| 磁盘 | 100G | 页图是主要占用（200dpi ≈ 300KB/页） |
| 单文档索引 | 50 页 ≈ 40–90s（有文本层）/ 3–6 分钟（扫描件走 CPU OCR） | 慢在 OCR，异步所以无感 |
| API 成本 | 开发期 0（Ollama）；终版只跑 B0/B6 各 300 题 ≈ 600 次调用 ≈ 3M token | 量级几十元；先跑 20 题估算单价 |

**成本公式**（写进报告，不写具体单价）：`单次成本 = P(L3)×页面token×图单价 + 文本token×单价 + 检索算力摊销`

## 8. 评测体系：怎么把"52%→79%"变成可信数字

### 8.1 数据集构成

| 子集 | 题量 | 来源 | 考查 |
|---|---|---|---|
| S1 中文财报 | 150 | 公开年报 | 主体场景 |
| S2 政务/招投标 | 60 | 公开文件（含扫描件） | 版式鲁棒性 |
| S3 英文对照 | 40 | DocVQA / ChartQA 抽样 | 方法可迁移性 |
| S4 不可回答 | 50 | 人工构造（问不存在的数据） | 拒答能力 |
| **合计** | **300** | | |

### 8.2 题型分层（每类 ≥ 30 题）

| 类型 | 例子 | 难点 |
|---|---|---|
| T1 单块事实 | "审计机构是谁" | 简单，作 sanity check |
| T2 表格数值 | "Q3 营收同比多少" | 表头 + 单位 + 口径 |
| T3 表格推理 | "哪一年毛利率最高" | 跨行比较 |
| T4 图表理解 | "图 2 的实验设置" | 需要视觉 |
| T5 跨页/多跳 | "对比 2022/2023 的现金流" | 证据分散 |
| T6 不可回答 | "2025 年的营收" | 拒答 |

### 8.3 指标定义（写死在报告里，防止被质疑）

| 指标 | 定义 | 判定方式 |
|---|---|---|
| **Answer Acc** | 数值类：数值 + 单位 + 口径全对（容差按原文精度）；文本类：关键实体齐全且无矛盾 | rubric LLM-judge + 30% 人工复核，分歧以人工为准 |
| **ANLS** | 与 DocVQA 对齐的编辑距离相似度 | 脚本，阈值 0.5 |
| **Recall@k** | 金标证据块是否在 top-k | 脚本（块级匹配） |
| **Citation P** | 每个 `[En]` 所指块是否蕴含该句 | 小模型打分 + 抽检 |
| **Citation R** | 每个关键结论是否都有引用 | 脚本 + 抽检 |
| **Refusal Acc** | T6 题正确拒答比例 | 脚本 |
| **误拒率** | T1-T5 中被错误拒答的比例 | 脚本 |
| **p95 延迟** | 首字 / 完整答案分开报 | 压测 |
| **成本** | 每 100 次问答 token 成本 | trace 汇总 |

### 8.5 统计可信度（防止被问穿）

- 300 题做 **bootstrap 1000 次重采样**，报 95% 置信区间（约 ±5pp）
- 前后对比用 **McNemar 配对检验**（同一批题、二分类结果）
- 结论必须写成："B4 相对 B3 提升 11.3pp（95% CI: 6.8–15.9, McNemar p<0.001, n=300）"
- 保存每次运行的 `predictions.jsonl`（含 prompt 版本、模型版本、seed），保证可复现

> 这一节是**区分"学生项目"和"工程报告"的分水岭**。面试官听到 McNemar 和置信区间，基本不会再追问"是不是运气好"。

### 8.6 错误分类法（10 类，错误归因的骨架）

| 码 | 类型 | 典型现象 |
|---|---|---|
| E1 | 解析丢失 | 表格没识别出来 / OCR 错字 |
| E2 | 切分切断 | 证据跨两个块，都没包含完整信息 |
| E3 | 表头错配 | 数字对上了，但列是"同比"不是"环比" |
| E4 | 检索未召回 | 金标块没进 top-20 |
| E5 | 排序挤出 | 进了 top-20 但没进 top-5 |
| E6 | 生成读错 | 检索到了，模型算错/读错 |
| E7 | 引用错位 | 答案对，但引用指向别的块 |
| E8 | 拒答错误 | 该拒没拒 / 不该拒却拒 |

### 10.2 五个真正的难点（提前想清楚）

**难点 1：表格的"结构"到底要保留到什么程度？**
保留太多 → prompt 爆炸；保留太少 → 丢表头。**解法**：双视图——检索用「表头 + 关键行摘要」，生成用「压缩 HTML（去样式、保留 span）」，两者由同一份 cells 派生。

**难点 2：跨页表格（财报高频）**
检测信号：相邻页、表头文本相似度 > 0.8、列数一致、无新标题。合并失败时的兜底：把两页一起作为证据返回，让模型自己拼。

**难点 3：VLM 读图表的"读数"不可靠**
不要指望 VLM 精确读数。**解法**：图表题优先返回"图 + caption + 邻文"，答案表述为"根据图 2，趋势是…"，并降低数值精确性要求；或者对图表做专门的"坐标轴 OCR"补充。**诚实地在报告里写"图表类是我们最弱的一档"**——这反而是加分项。

**难点 4：引用校验的误判**
小模型判"蕴含"容易过严或过松。**解法**：两级——规则校验（答案中的数字/实体是否出现在引用块）+ LLM judge 兜底，只在规则不确定时调用。

**难点 5：长文档的索引时间**
50 页 40-90s 可接受，500 页就 10 分钟+。**解法**：分页并行（进程池）+ 增量索引（按页 hash）+ 失败页单独重试。这也解释了为什么必须异步。
